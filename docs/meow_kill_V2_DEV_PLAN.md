## 三、总体策略

1. **保留**：Nakama Match、opcode、快照广播、自建匹配队列思路；Godot 桌布 / 座位 / 手牌 / 确认栏 / 战报日志等外壳。
2. **分叉建议**：新规与现行简化玩法并存成本高时，优先考虑 **`meow_kill` 新 label**（例如 `meow_kill_cat`）或 **`Modules/src/games/meow_kill_v2/`** 目录，避免无限兼容分支。
3. **权威**：状态与随机仅在服务端；客户端只发意图。
4. **分期交付**：先可玩的规则子集，再叠装备与高复杂度猫种。

## 四、分期路线图（里程碑）

以下为推荐顺序；每项完成后在下方「里程碑状态」打勾或填日期。

### 阶段 A — 规则与数据冻结（策划 + 程序可读规格）

- 输出机器可读：**牌 ID、名称、类型、数量、效果枚举**；**3–6 人身份配置表**；**猫种技能触发时机表**。
- 卡牌表格建议：**CSV/JSON + 校验脚本**（数量合计 90、无重复 ID）。
- Godot 资源路径约定：**牌背、喵叫图标、装备、猫种立绘** 命名规则。

**产出物**：规则附录或独立 `data/meowkill_cards.schema.json`（待立项）。

### 阶段 B — 服务端核心壳（空桌可循环）

- **状态**：人数 3–6；身份四阵营；`hp/max_hp/hand`；`equipment`（0～1）；`cat_breed`；全局 `deck/discard`。
- **阶段机**：`draw → play → discard → advance`（与规则「三步走」对齐；判定区等可后置）。
- **摸牌**：默认摸 2；优先接入 **橘猫**「摸牌多摸 1」作为首个技能样本。
- **基础互动**：**抓挠 → 询问闪躲 → 伤害 →（可选简化濒死）**。
- **胜负主干**：至少 **家猫阵亡 / 野猫方胜利** 一条路径可跑通。

**产出物**：`Modules` 内单元测试或脚本测试（洗牌、合法目标、胜负）。

### 阶段 C — 喵叫牌与装备

- **喵叫**：建议顺序——小鱼干、逗猫棒、炸毛 → 飞奔、咬咬（咬咬需「不可闪躲」语义）。
- **装备**：四人四规则；实现「一人一件、新顶旧弃」；效果按依赖：**毛线球（距离）→ 纸箱 → 猫爬架 → 激光笔（与摸牌阶段交互）**。
- **pending 扩展**：逗猫棒随机抽牌、激光笔看手牌等需协议字段或子 opcode。

**产出物**：FAQ（英短迟钝、布偶威吓 vs 猫爬架顺序）对应测试用例标题列表。

### 阶段 D — 猫种技能引擎（最小可行）

- 抽象窄接口：`SkillContext`（触发时机 + 参数），如 `on_damage`、`on_become_slash_target`、`on_play_phase`、`once_per_game`。
- **接入顺序建议**：橘 → 黑 → 白 → 暹罗 / 英短 / 布偶 / 狸花 / 无毛。
- **AI**：先合法随机，再启发式；独行猫推理非首版目标。

### 阶段 E — Godot 客户端新版 UI/UX

- 术语与新卡牌图资源全局替换（抓挠 / 闪躲等）。
- 装备区、攻击范围提示、猫种与身份简报。
- 体力展示与「家猫 4 / 其余 3」一致。

### 阶段 F — 联调与发布

- 匹配参数：`player_count`、人机补齐策略。
- 快照体积、`event_log` 长度与频率复查。
- **变体规则**（换座、双猫种、快速模式）默认关闭或独立开关。
